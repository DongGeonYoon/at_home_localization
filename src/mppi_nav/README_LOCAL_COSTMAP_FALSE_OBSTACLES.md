# Local Costmap: 로봇 주변에 생기는 원형 cost (거짓 장애물) 분석과 해결

작성일: 2026-10-05
대상: `/local_costmap/costmap`, `/mppi_static_costmap/costmap`을 만드는 쪽과 사용하는 MPPI 팀

---

## 1. 증상

- 아무것도 없는 곳인데 로봇 footprint 바로 옆에 작은 lethal 셀이 생깁니다.
- 그 셀에 inflation이 붙어서 원형 cost가 됩니다.
- 원이 생기면 MPPI가 갑자기 회피합니다.
- 로봇이 정지해 있어도 작은 원이 생겼다 사라집니다.

---

## 2. 결론 요약

| # | 원인 | 상태 |
|---|---|---|
| ① | FAST-LIO localization 전처리의 `blind` 조건식 버그 → 근거리 점이 걸러지지 않음 | ✅ 수정, 실측 확인 |
| ② | local costmap이 원시 cloud를 그대로 장애물로 사용 → 로봇 몸체 점이 장애물로 표시됨 | ✅ 수정 (self_filter), 실측 확인 |
| ③ | footprint 원(r 0.37)이 몸체 반사를 덮지 못함 → 원 바로 바깥에 lethal 셀이 남음 | ✅ ②로 해결 |
| ④ | 로봇 뒤쪽 사각지대에 찍힌 셀이 지워지지 않음 | ⏳ 미수정 (STVL 제안) |
| ⑤ | LiDAR 높이의 낮은 물체 가장자리와 오른쪽 몸체 반사 때문에 작은 셀이 깜빡임 | ⏳ 미수정 (설정 2개 제안) |
| ⑥ | ICP 보정으로 위치가 점프할 때 남는 흔적, Livox 노이즈 | ❓ 정지 상태에서는 확인 불가, 주행 시험 필요 |

**스크린샷과 문서에서 보고된 "footprint 옆의 원"은 ①+②+③이 겹친 것이었고, 이 부분은 수정했습니다.**
④⑤는 같은 모양의 증상을 만드는 별개의 원인이며, 아직 수정하지 않았습니다.

## 3. 해결된 원인 (①②③)

### 3.1 원인

**① `blind`(근거리 제거)가 동작하지 않음**
`src/FAST_LIO_LOCALIZATION2/src/preprocess.cpp` (Livox handler)

```cpp
// 수정 전: && 가 z 항에만 묶임 → 중복 점 검사만 통과하면 거리 조건을 보지 않음
if ((abs(x - x_prev) > 1e-7) || (abs(y - y_prev) > 1e-7) ||
    (abs(z - z_prev) > 1e-7) && (x*x + y*y + z*z > blind * blind))

// 수정 후: 매핑 패키지(FAST_LIO_ROS2)와 같은 식
if (((abs(x - x_prev) > 1e-7) || (abs(y - y_prev) > 1e-7) || (abs(z - z_prev) > 1e-7)) &&
    (x*x + y*y + z*z > blind * blind))
```

- 설정에는 `blind: 0.5`가 있었지만 실제로는 0이었습니다.
- 그래서 로봇 몸체에 맞은 점이 모두 `/cloud_registered_body`로 나갔습니다.

**② 원시 cloud를 그대로 장애물로 사용**
- `local_costmap.yaml`의 marking 입력이 `/cloud_registered_body`였습니다.
- 장애물 높이대(바닥 기준 약 10~120 cm)에 베이스 윗면(44.5 cm)과 상단 구조물(93 cm)이 모두 들어갑니다.
- `mark_threshold: 0`이므로 점 1개만 있어도 lethal입니다.

**③ footprint clearing이 몸체를 덮지 못함**
- Nav2는 footprint 안의 셀만 매 주기 비웁니다.
- footprint 원의 반지름(0.37 m)이 베이스 모서리까지의 거리(0.368 m)와 거의 같습니다.
- LiDAR가 앞쪽 끝(x 0.31 m)에 달려 있어서, LiDAR 장착부와 모서리에서 나온 반사점이 원의 경계 바로 바깥(0.37~0.40 m)에 남습니다.

### 3.2 실측 근거 (LiDAR 연결, 로봇 정지)

수정 전 설정을 가정하고 원시 cloud로 계산했습니다.

| 항목 | 값 |
|---|---|
| 로봇 몸체에 맞은 점 | 스캔당 459개 |
| 그중 LiDAR 0.5 m 이내 | 449개 (`blind`가 동작했다면 걸러졌을 점) |
| footprint 원 바깥이면서 장애물 높이대인 몸체 점 | 스캔당 10.7개 |
| 그 점이 찍히는 셀 | base_link (x +0.25, y -0.25 ~ -0.30), **앞쪽 오른쪽 모서리**, 매 스캔 100% |

이 셀이 매 스캔 lethal로 다시 찍히고 inflation이 붙어서, footprint 모서리에 붙은 원으로 보였습니다.

### 3.3 수정 내용

| 파일 | 변경 |
|---|---|
| `FAST_LIO_LOCALIZATION2/src/preprocess.cpp` | 위의 조건식 괄호 수정 |
| `FAST_LIO_LOCALIZATION2/config/mid360.yaml` | `blind` 0.5 → **0.2 m**. 0.5로 두면 로봇 앞 약 0.45 m 안의 실제 장애물도 사라짐. 몸체 점은 self_filter가 제거 |
| `mppi_nav/mppi_nav/self_filter.py` (신규) | base_link 기준 상자 안의 점을 제거해서 `/local_obstacle_cloud`로 발행. numpy 벡터 연산, frame은 `body` 그대로 |
| `mppi_nav/config/local_costmap.yaml` | marking 입력 `/local_obstacle_cloud`, `obstacle_min_range` 0.0 → 0.10, `min_obstacle_height` -0.30 → -0.25, `obstacle_max_range` 6.0 → 4.0 |
| `mppi_nav/launch/slam_costmap_bringup.launch.py` | self_filter 노드와 인자 추가 |
| `mppi_nav/rviz/costmap_bringup.rviz` | Raw Body Cloud(빨강, 기본 꺼짐), Local Obstacle Cloud(노랑), Robot Footprint 표시 |

self_filter 상자 (base_link 기준, launch 인자 `self_filter_*`로 변경 가능):

| | min | max | 근거 |
|---|---|---|---|
| x | -0.32 | 0.40 | 베이스 길이 0.54 m, LiDAR 앞면 약 0.35 m, 여유 5 cm |
| y | -0.30 | 0.30 | 베이스 폭 0.50 m, 여유 5 cm |
| z | -0.05 | 1.00 | 바닥 ~ 상단 구조물 0.93 m |

- clearing은 원시 cloud(`/cloud_registered_body`, 별도 source `lidar_clear`)를 그대로 씁니다. 장애물을 지우는 광선이 줄지 않습니다.
- self_filter를 끄고 비교하려면 `run_local_cloud_filter:=false`를 붙입니다. 그러면 수정 전처럼 원시 cloud가 costmap에 들어갑니다.

## 4. footprint 변경 (원 → 실제 모양)

장애물 주변 cost 범위를 줄이기 위해 `robot_radius: 0.37` 원 대신 실제 모양의 polygon을 씁니다 (static, local 공통).

```yaml
footprint: [[0.35, 0.05], [0.35, -0.05], [0.27, -0.05], [0.27, -0.25],
            [-0.27, -0.25], [-0.27, 0.25], [0.27, 0.25], [0.27, 0.05]]
```

| 장애물로부터 거리 | 이전 (원 0.37) | 지금 |
|---|---|---|
| 0 ~ 0.25 m | 99 | 99 |
| 0.30 m | 99 | 82 |
| 0.35 m | 99 | 67 |
| 0.368 m (모서리 반경) | 99 | 65 |
| 0.40 m 이상 | 0 | 0 |

- static costmap의 99 셀: 23,066 → 18,023 (-22%)
- `inflation_radius`(0.40)는 모서리 반경(0.368)보다 커야 해서 그대로 두었습니다.

> ⚠️ **MPPI 팀:** `data >= 99`만으로 충돌을 판단하면, 로봇 중심이 장애물에서 0.25~0.368 m 떨어진 상황의 **모서리 충돌을 놓칩니다.**
> footprint 다각형이 덮는 셀 중 하나라도 `100`이면 충돌로 처리해야 합니다 (Nav2 MPPI `CostCritic`의 `consider_footprint: true`와 같은 방식).

## 5. 남은 원인과 해결 방안

### ④ 로봇 뒤쪽 사각지대 흔적 (미수정)

**증상:** 사람이나 노트북이 로봇 뒤에 있다가 사라져도, 그 자리의 lethal 셀과 원이 계속 남습니다.

**실측:**
- 로봇 뒤 0.4~0.9 m의 lethal 셀 111개 중 **86개는 지금 그 자리에 점이 없음**
- 그 영역의 장애물 높이대를 지나는 광선: 스캔당 약 10개 (전체 5,585개 중)

**원인:**
- LiDAR가 앞쪽 끝에 있고 바로 위에 93 cm 구조물이 있어서, 로봇 뒤쪽은 몸체에 가려 거의 보이지 않습니다.
- Nav2 VoxelLayer는 광선이 다시 지나가야만 셀을 지웁니다. 보이지 않는 곳에 찍힌 셀은 영원히 남습니다.
- `mark_threshold: 0`이라서, 한 칸의 여러 높이 층 중 하나만 남아도 그 칸 전체가 lethal로 유지됩니다.

**영향:** 앞으로만 갈 때는 작습니다. 하지만 회전하거나 후진하면 흔적이 앞이나 옆으로 오면서 같은 회피 증상을 만들 수 있습니다.

**해결 방안 (권장):** VoxelLayer를 **STVL (`spatio_temporal_voxel_layer`)**로 교체하고 decay를 3~5 s로 둡니다.
- 일정 시간 다시 관측되지 않은 표시는 자동으로 사라집니다.
- 설치: `sudo apt install ros-humble-spatio-temporal-voxel-layer` (현재 미설치)
- 단점: 그 시간 동안 다시 보이지 않는 실제 장애물도 잊습니다. 사각지대는 원래 보이지 않는 곳이라 차이가 작습니다.

### ⑤ 정지 상태에서 깜빡이는 작은 원 (미수정)

**실측 (정지 30초):** 정적 지도에 없는 작은 lethal 덩어리가 30초 동안 97개, 프레임당 평균 12개 생겼다 사라졌습니다.

**⑤-a. 로봇 오른쪽 바로 옆 (약 0.33 m)**

| 측정 | 값 |
|---|---|
| 위치 (base_link) | y -0.31 ~ -0.35, x -0.14 ~ +0.26 |
| 높이 | 바닥 41~50 cm (베이스 윗면 높이) |
| 반사 강도 | 0~14 (매우 약함) |
| 빈도 | 간헐적 (2~32%) |

- self_filter 상자(y ±0.30)보다 1~5 cm 바깥이고 높이가 베이스 윗면과 같습니다. **몸체 오른쪽 모서리나 부착물의 반사**일 가능성이 높습니다.
- LiDAR 장착 오프셋(y 0.023 m) 때문에 로봇 중심이 왼쪽으로 약 2 cm 치우쳐 있어서 오른쪽 여유가 더 작습니다.

**⑤-b. 1~2.5 m 떨어진 곳의 깜빡임**
- 점이 **LiDAR와 같은 높이의 층(바닥 35~45 cm)에만** 있고, 반사 강도가 0~24로 약합니다.
- 기준 PCD에도 같은 자리에 있으므로, 매핑 때부터 있던 실제 물체입니다. 예를 들면 의자 좌판, 낮은 수납장, 박스 윗면처럼 높이가 LiDAR와 비슷한 물체입니다.
- 정적 지도는 바닥 0.55 m 이상만 투영하므로 이런 물체는 정적 지도에 없습니다.
- 깜빡이는 원리:
  1. 물체 윗면을 거의 수평으로 스치듯 보기 때문에 매 스캔 맞지 않습니다. Mid-360은 스캔마다 쏘는 방향이 달라지는 패턴이라 작은 표적은 듬성듬성 맞습니다.
  2. 맞지 않은 스캔에서는 같은 높이의 광선이 그 위를 지나가며 셀을 지웁니다.
  3. costmap은 갱신(5 Hz)마다 최신 스캔 하나만 씁니다(`observation_persistence: 0.0`).
- 즉 물체는 진짜인데 **표시가 불안정한 것**이 문제입니다.

**해결 방안:**

| 대상 | 변경 | 효과와 위험 |
|---|---|---|
| ⑤-a | self_filter `self_filter_min_y / max_y` ±0.30 → **±0.36** | 몸체 반사 제거. 0.30~0.36 m에 실제로 붙은 장애물은 이미 충돌 거리라 위험이 작음 |
| ⑤-b | marking source `observation_persistence` 0.0 → **0.5 s** (최근 약 5스캔을 합쳐서 표시) | 듬성듬성 맞는 실제 물체가 계속 표시되어 깜빡임이 없어짐. 지우는 쪽은 최신 스캔 그대로 → 물체가 사라질 때 최대 0.5 s 늦게 지워짐 |

**권장하지 않는 방법:** 층마다 최소 점 개수를 요구하거나 `mark_threshold`를 올리는 것.
이렇게 하면 얇은 책상 상판처럼 한 층에만 보이는 실제 장애물도 놓칩니다(로봇 높이 0.93 m).

**적용 전 확인할 것:**
1. 로봇 오른쪽 면, 바닥 45~50 cm 높이에 베이스 밖으로 튀어나온 것(케이블, 손잡이, 스위치 등)이 있는지. 있다면 footprint(y ±0.25)도 그만큼 넓혀야 합니다.
2. ⑤-b 위치에 높이 40~50 cm 물체가 실제로 있는지.

### ⑥ 확인하지 못한 원인

| 원인 | 확인 방법 |
|---|---|
| ICP 보정(1 Hz)으로 위치가 점프할 때 이전 위치 기준으로 찍힌 셀이 남음. 현재는 `/initialpose` 후에만 local costmap을 비움 | 주행 중 지도→odom 보정값(`/map_to_odom`)이 크게 바뀌는 순간과 흔적 생성이 겹치는지 기록 |
| Livox 노이즈 태그(공간/강도 신뢰도 비트) 미사용. 현재는 다중 반사 비트(0x30)만 거름 | LiDAR 높이 점의 6%, 다른 높이 2%가 노이즈 태그. 주원인은 아님 |

## 6. 관련 수정: `/cur_scan_in_map`이 진행 방향 뒤로 밀려 보이던 문제

원형 cost와 별개지만, RViz에서 위치추정이 틀린 것처럼 보이게 만들던 문제라 함께 기록합니다.

- **원인:** `global_localization.py`가 단일 스레드에서 스캔 처리와 ICP(0.3 s 이상)를 같이 했습니다. ICP 동안 스캔이 큐(depth 10)에 쌓였다가 늦게 발행됐습니다.
- **수정:** 구독 큐 depth 1, ICP를 별도 callback group으로 분리(MultiThreadedExecutor), 스캔 콜백은 numpy 행렬 곱만 수행
- **결과 (큰 맵 `lab_map.pcd`, 30초):**

| | 지연 평균 | p95 | 최대 |
|---|---|---|---|
| 수정 전 | 0.099 s | 0.356 s | 0.450 s |
| 수정 후 | 0.037 s | 0.055 s | 0.075 s |

- costmap이 쓰는 TF(`map → camera_init`)는 원래 이 지연의 영향을 받지 않았습니다. `transform_fusion`이 FAST-LIO 시각으로 50 Hz 발행하기 때문입니다.
